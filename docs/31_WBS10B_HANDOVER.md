## 3. 남은 작업 3개

### 3.1 알림 2단계 — 서버에 남는 알림함

**지금 상태.** 1단계는 프론트 전용입니다. 받은 알림을 `localStorage`에 최근 20건만 남기므로
**다른 기기에서는 보이지 않고, 저장소를 지우면 사라집니다.** 그 한계를 목록 하단에
"최근 알림만 이 기기에 보관해요"로 적어 뒀습니다.

**해야 할 것.**

- `notifications` 테이블 + 조회 API (`GET /api/members/me/notifications`)
- 읽음 처리 API
- 서버가 알림을 만드는 지점 — 지금 WebSocket을 쏘는 자리(`MatchingStateChangedEventHandler`)에
  붙이면 한곳에서 끝납니다
- 프론트의 `notificationStore`를 서버 목록과 합치기

**착수 전에 정할 것.**

| 항목 | 고민할 거리 |
| --- | --- |
| 보관 기간 | 무한히 쌓으면 조회가 느려진다. 30일? 100건? |
| 어떤 알림을 저장할지 | `MEMBER_ARRIVED` 같은 중간 상태까지 남기면 목록이 시끄럽다 |
| **행위자 id** | 지금 알림에는 "누가 했는지"가 없다. 그래서 내가 도착을 눌러도 나에게 `MEMBER_ARRIVED`가 온다. 2단계에서 `actorMemberId`를 실으면 문구를 정확히 할 수 있다 |
| 읽음의 단위 | 지금은 "목록을 열면 전체 읽음"이다. 개별 읽음이 필요한가 |

**주의.** WebSocket과 저장을 **같은 자리에서** 하되, 저장 실패가 실시간 알림을 막지 않게
해야 합니다. 매너온도 보상이 `AFTER_COMMIT` + 별도 transaction으로 분리된 것과 같은 이유입니다
(`MannerTemperatureRewardService` 주석 참고).

### 3.2 알림 3단계 — PWA Web Push

**앱이 꺼져 있어도** 알림이 갑니다. 가장 필요한 것은 `MATCH_PROPOSED`입니다 — 응답 시간이
30초이고 놓치면 `penalty_score +1`에 쿨타임 2분이 붙습니다.

**해야 할 것.**

| 항목 | 내용 |
| --- | --- |
| VAPID 키 | 생성 후 환경변수로 주입. **저장소에 넣지 않는다** |
| 구독 저장 | `push_subscriptions` 테이블(endpoint, p256dh, auth, member_id) |
| 발송 | backend에 web-push 라이브러리 추가 |
| service worker | 지금은 workbox `generateSW`라 `push` 핸들러를 넣을 수 없다. **`injectManifest`로 전환** 필요 |
| 권한 요청 | 브라우저 알림 권한을 언제 물을지. 첫 매칭 신청 직전이 자연스럽다 |

**iOS 제약.** Safari는 **홈 화면에 설치해야만** push가 옵니다(16.4+). 설치 유도 안내가 필요할 수
있습니다.

**주의.** `vite.config.ts`의 `VitePWA` 모드를 바꾸는 작업이라 기존 캐싱 동작에 영향이 갑니다.
바꾼 뒤 오프라인 동작을 한 번 확인하세요.

### 3.3 4.9 PR C — 30도 매칭 제한

**지금 상태.** 미착수입니다. `MatchPoolEntryService.enter()`에 온도 검사가 **없습니다**.
매너온도가 20도여도 매칭됩니다.

**이미 정해진 것**(`docs/19` 4.9).

- 신고 확정 1건당 차감은 `-5.00`에서 **`-2.00`으로 낮춰 뒀습니다.** 30도 아래가 되려면 신고
  4건이 필요해, 관리자 안전 알림(3건)이 **먼저** 뜨고 그다음 자동 제한이 걸립니다. 이 순서가
  4.3에서 정한 "자동 제한은 회원 status를 바꾸지 않고 관리자 알림까지만"을 지킵니다
- 회복 경로 두 개가 이미 있습니다 — 만남 완료 보상(`+0.50`), 시간 경과 회복(30일 주기,
  36.50까지). 이게 없으면 **"신고 4건 → 매칭 금지 → 만남 불가 → 회복 불가"** 데드락이 됩니다

**해야 할 것.**

- `MatchPoolEntryService.enter()`에 온도 조건 추가
- `MatchingRestrictionResponse`에 제한 상태 추가
- 프론트 `useMatchingSession`의 상태 파생과 라우팅 — 새 제한 상태가 **실제로 화면에 도달하는지**
  끝까지 따라가야 합니다. 지금 restriction 응답에서 화면 상태를 파생하는 구조입니다

**착수 전에 정할 것 — 이것이 핵심입니다.**

> **제한에 걸린 사람에게 무엇을 보여줄 것인가.**

쿨타임처럼 카운트다운을 보여줄 수도, "매너온도가 낮아 잠시 매칭할 수 없어요"로만 알릴 수도
있습니다. **온도가 낮은 이유는 곧 "신고를 받았다"**이므로, 얼마나 드러낼지가 `docs/19` 4.8의
신고자 보호와 얽힙니다. 회복 방법(만남 완료 / 시간 경과)을 안내할지도 함께 정하세요.

## 5. 알려진 한계 — 문서에만 남긴 것

이어받는 사람이 "버그 아닌가?" 하고 다시 조사하지 않도록 적어 둡니다.

| 한계 | 내용 | 왜 그대로 뒀나 |
| --- | --- | --- |
| 노쇼 페널티 면제 | 혼자 도착한 사람이 일찍 나가면 미도착자가 노쇼 판정을 피한다 | 고치려면 "끝난 매칭에 30분 뒤 페널티"라는 흐름이 필요하다. 기다린 사람은 `NO_SHOW` 사유로 **신고할 수 있어** 구제 경로는 있다 |
| 알림 자기 반향 | 내가 도착을 눌러도 나에게 `MEMBER_ARRIVED`가 온다 | 서버가 행위자 id를 안 보낸다. 같은 화면에 있으면 토스트가 억제돼 실제로는 안 보인다. **2단계에서 해결** |
| 1단계 알림 보관 | 기기마다 다르고 최근 20건뿐 | 2단계 범위. 화면에 한계를 적어 뒀다 |
| 도착 좌표 신뢰 | 브라우저가 보낸 좌표를 그대로 믿는다 | 조작하려면 둘 다 현장 체크인 + 매칭 성사 + 1시간에 한 번이라 수지가 안 맞는다 |

## 6. 개발 환경과 주의할 규칙

### 테스트 돌리기

```bash
cd backend
JAVA_HOME=<JDK 17> ./gradlew test        # Docker Desktop 필요(Testcontainers)
cd ../frontend
npx vitest run && npx tsc -b
```

**JDK 17이어야 합니다.** 기본 JDK가 8이면 gradle이 실패합니다.

**baseline 실패 2건은 정상입니다** — `ContentBookmarkCommentIntegrationTest`(만료 쿠키 401),
`FestivalRepositoryIntegrationTest`(`@Sql` 문제). 그 둘 말고 실패가 나오면 내 변경 탓입니다.

### migration — 세 번 사고가 났습니다

`V28~V30`, `V35`, `V36`·`V37`이 **저장소에 없는 채 공유 dev DB에 먼저 적용**돼, 그때마다 우리
번호를 옮겨야 했습니다(`docs/10` 사고 기록).

- 번호는 **저장소 파일 목록이 아니라 공유 dev DB의 `flyway_schema_history`를 조회해서** 정한다
- **push하지 않은 migration을 공유 dev DB에 적용하지 않는다**
- `flyway repair`를 쓰지 않는다. 남의 migration을 내 파일로 위장시켜 그쪽 변경을 이력에서 지운다
- 테스트 계정·인증 정보 주입은 migration이 아니라 `scripts/`의 SQL로 둔다

### 공유 dev DB

**조회만 합니다.** 시간 조작이나 초기화가 필요하면 로컬 DB를 쓰세요(`docs/30` 4.0).

### 브랜치

`dev`에서 분기하고 PR로 `dev`에 병합합니다. `main`으로 직접 올리지 않습니다(`docs/12`).
