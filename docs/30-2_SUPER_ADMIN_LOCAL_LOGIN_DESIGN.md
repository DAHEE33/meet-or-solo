# 슈퍼관리자 ID/PW 로그인 설계

- 상태: `DONE` — 구현 완료(수동 검증 대기). 2026-09-14.
- 관련 문서: [보안 정책](06_SECURITY_POLICY.md), [관리자·회원·안전 로드맵](19_ADMIN_MEMBER_SAFETY_ROADMAP.md)

## 1. 배경과 목표

현재 관리자 화면(`/admin/*`)은 Kakao/Naver SSO로 로그인한 뒤 `members.role = 'ADMIN'`인
계정만 들어갈 수 있습니다. 소셜 로그인 제공자가 장애이거나, 관리자 계정을 소셜 계정과
분리해서 운영하고 싶을 때 대체 진입 경로가 없습니다.

목표는 **SSO를 유지한 채 진입 경로를 하나 더 추가**하는 것입니다.

- `/admin/login` 화면에서 아이디·비밀번호로 로그인한다.
- 로그인에 성공하면 기존 SSO 로그인과 **완전히 같은 세션**(access/refresh cookie)을 얻는다.
- 기존 SSO 관리자 로그인은 그대로 둔다. 둘 중 아무 경로로 들어와도 관리자 기능은 동일하다.

비목표(이번 범위 아님): 관리자 2단계 인증, 비밀번호 자체 변경 화면, 관리자 계정 다중 생성 UI.

## 2. 현재 구조 분석

| 계층 | 현재 동작 | 위치 |
| --- | --- | --- |
| 로그인 | OAuth 콜백 → `AuthService.issueTokens()` → `access_token`/`refresh_token` HttpOnly cookie | `AuthController`, `AuthService` |
| 토큰 | 자체 HMAC-SHA256 JWT. claim에 `sub`/`role`/`status` | `JwtProvider` |
| 권한 판정 | 토큰의 `role`을 신뢰하지 않고 `members.role`을 DB에서 재조회 | `AdminAuthorizationService.requireAdmin` |
| 요청 진입 | `MemberAccessInterceptor`가 `/api/**`에서 제재 상태 검사(`/api/auth/**`, `/api/health` 제외) | `WebMvcConfig` |
| 관리자 화면 | `AdminRoute`가 `GET /api/admin/me` 호출 → 200 통과, 403 "권한 없음" | `AdminRoute.tsx` |

핵심은 **모든 관리자 기능이 `memberId` 하나로 동작**한다는 점입니다. `admin_actions.admin_member_id`가
`members(id)` FK `NOT NULL`이고, 신고 처리·회원 제재·문의 답변이 전부 이 값을 감사 로그로 남깁니다.

## 3. 핵심 설계 판단

> **슈퍼관리자도 `members` row 1건에 매핑한다. 인증 수단만 비밀번호로 하나 늘린다.**

별도 `AdminPrincipal` 개념을 만들면 감사 로그 FK, 제재 서비스, 문의 답변자, WebSocket principal까지
"회원이 아닌 관리자" 분기를 전부 추가해야 합니다. `provider = 'LOCAL'` 회원 1행으로 두면
**로그인 입구만 늘어나고 그 뒤 코드는 하나도 바뀌지 않습니다.**

```text
[기존] Kakao/Naver OAuth ─┐
                          ├─→ issueTokens() → access_token cookie → 기존 관리자 API 전부
[추가] ID/PW 로그인       ─┘        (이 지점부터 완전히 동일)
```

## 4. DB 설계

`V37__add_admin_local_credentials.sql`.

**처음에는 V36에 이어 붙였다가 되돌렸다.** V36은 이미 dev DB에 적용된 상태였고, 적용된
migration의 내용을 바꾸면 checksum이 달라져 Flyway validate가 실패한다(실제로 통합 테스트
34건이 `Migration checksum mismatch for migration version 36`으로 깨졌다). 되돌리려면 공용
dev DB의 history를 손봐야 하므로 파일을 나눴다. **적용이 끝난 migration은 수정하지 않는다.**

```sql
-- 1) provider에 LOCAL 허용 (V6과 같은 방식)
ALTER TABLE members DROP CONSTRAINT chk_members_provider;
ALTER TABLE members ADD CONSTRAINT chk_members_provider
    CHECK (provider IN ('KAKAO', 'NAVER', 'LOCAL'));

-- 2) 비밀번호 자격증명 (members와 1:1)
CREATE TABLE admin_credentials (
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY,
    member_id       BIGINT       NOT NULL,
    username        VARCHAR(50)  NOT NULL,
    password_hash   VARCHAR(100) NOT NULL,   -- BCrypt
    failed_attempts INTEGER      NOT NULL DEFAULT 0,
    locked_until    TIMESTAMPTZ,
    last_login_at   TIMESTAMPTZ,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_admin_credentials PRIMARY KEY (id),
    CONSTRAINT uq_admin_credentials_member UNIQUE (member_id),
    CONSTRAINT uq_admin_credentials_username UNIQUE (username),
    CONSTRAINT fk_admin_credentials_member
        FOREIGN KEY (member_id) REFERENCES members (id) ON DELETE RESTRICT
);
```

### 계정 자체를 마이그레이션에 넣지 않는 이유

비밀번호 해시라도 저장소에 커밋되면 `docs/06_SECURITY_POLICY.md`의 Secret 규칙 위반입니다.
계정을 바꿀 때마다 마이그레이션을 추가해야 하는 문제도 생깁니다. 계정 생성은 5장의
환경변수 부트스트랩으로 처리합니다.

### `members` row의 값

| 컬럼 | 값 |
| --- | --- |
| `provider` | `LOCAL` |
| `provider_user_id` | 로그인 아이디(username)와 같은 값 |
| `role` | `ADMIN` |
| `status` | `ACTIVE` |
| `nickname` | `ADMIN_LOCAL_NICKNAME` 환경변수 값. 일반 회원과 겹치지 않는 값을 쓴다 |

## 5. 계정 생성과 비밀번호 회전 — 환경변수 부트스트랩

`SuperAdminAccountBootstrap`(`ApplicationRunner`)

```text
ADMIN_LOCAL_USERNAME / ADMIN_LOCAL_PASSWORD 가 둘 다 있을 때만 동작
  → members upsert   (provider='LOCAL', provider_user_id=username, role='ADMIN', status='ACTIVE')
  → admin_credentials upsert (password_hash = BCrypt(password))
둘 중 하나라도 비어 있으면 아무것도 하지 않는다 (기본 계정 자동 생성 금지)
```

- **비밀번호 변경·회전도 같은 경로**다. 환경변수를 바꾸고 재기동하면 해시가 갱신된다.
  별도 비밀번호 변경 화면을 만들지 않는 이유가 이것이다.
- 평문 비밀번호는 어떤 경우에도 로그에 남기지 않는다.
- local 환경에서만 짧은 값(`admin` 등)을 쓰고, dev/prod에는 강한 값을 별도로 주입한다.

## 6. API 설계

```text
POST /api/auth/admin/login    { "username": "...", "password": "..." }
     → 200 + access_token / refresh_token cookie (기존 tokenCookie와 동일한 속성)
     → 실패는 전부 401 ADMIN_LOGIN_FAILED

POST /api/auth/logout         기존 endpoint 재사용 (추가 작업 없음)
POST /api/auth/refresh        기존 endpoint 재사용 (refresh_tokens는 member_id 단위)
GET  /api/admin/me            기존 endpoint 재사용 (AdminRoute가 이미 사용 중)
```

### 경로를 `/api/auth/admin/login`에 두는 이유

`/api/admin/...` 아래가 아니라 `/api/auth/**` 아래에 둔다. 세 가지가 모두 이 접두에 맞춰져 있다.

1. `WebMvcConfig`가 `/api/auth/**`를 `MemberAccessInterceptor`에서 제외한다. 제재된 소셜 계정의
   cookie가 브라우저에 남아 있으면 관리자 로그인 시도 자체가 제재 예외로 막힐 수 있다.
2. Frontend `apiClient`의 `AUTH_PATH_PREFIX`가 이 접두의 401에서 자동 refresh 재귀를 막는다.
3. `SecurityConfig`의 permitAll 목록과 일관된다.

### 로그인 검증 순서

```text
1. username 조회 — 없으면 더미 해시로 BCrypt 비교 후 실패 (계정 존재 여부의 응답 시간 차이 축소)
2. 잠금 확인 — locked_until 이 현재보다 미래면 실패
3. BCrypt 비교 — 실패 시 failed_attempts += 1, 5회 도달 시 locked_until = now + 10분
4. members.role = 'ADMIN' 재확인 + MemberAccessPolicy.requireAccessible
5. 성공 — failed_attempts=0, locked_until=NULL, last_login_at 기록 후 issueTokens()
```

실패 응답은 아이디 오류·비밀번호 오류·잠금·권한 없음을 구분하지 않고 전부 같은
`401 ADMIN_LOGIN_FAILED`로 내보낸다. 구분해서 알려주면 아이디 목록을 열거할 수 있다.

### 구성 요소

| 클래스 | 역할 |
| --- | --- |
| `AdminCredential` | `admin_credentials` 엔티티. 실패 누적·잠금·성공 초기화를 엔티티 메서드로 가진다 |
| `AdminCredentialRepository` | `findByUsername` |
| `AdminLoginService` | 위 검증 순서. 성공 시 `AuthService`의 토큰 발급 재사용 |
| `AdminAuthController` | `POST /api/auth/admin/login`. cookie 발급은 기존 `AuthController`와 같은 속성 |
| `SuperAdminAccountBootstrap` | 5장의 환경변수 부트스트랩 |

`SecurityConfig`에 `BCryptPasswordEncoder` 빈을 추가한다(`spring-boot-starter-security`는 이미 의존성에 있다).

## 7. Frontend 설계

| 변경 | 내용 |
| --- | --- |
| `/admin/login` 라우트 추가 | `AdminLoginPage` — 아이디·비밀번호 폼, 실패 안내, 성공 시 `/admin` 이동 |
| `apiClient` 401 분기 | **필수**. 현재는 모든 401을 `/login`으로 보낸다. `pathname`이 `/admin`으로 시작하면 `/admin/login`으로 보낸다 |
| `AdminRoute` | 403 화면(권한 없는 소셜 계정)은 유지하고 "관리자 계정으로 로그인" 링크만 추가 |
| `AdminHeader` | 로그아웃 버튼 추가. 기존 `POST /api/auth/logout` 재사용 |

일반 `/login` 화면에는 관리자 로그인 링크를 노출하지 않는다.

## 8. 보안 고려

- 실제 아이디·비밀번호는 저장소에 넣지 않는다. `ADMIN_LOCAL_USERNAME`, `ADMIN_LOCAL_PASSWORD`,
  `ADMIN_LOCAL_NICKNAME`을 `docs/06_SECURITY_POLICY.md`의 GitHub Secrets 목록에 추가한다.
- 비밀번호는 BCrypt로만 저장한다. 평문·가역 암호화를 쓰지 않는다.
- 연속 실패 5회 → 10분 잠금. 잠금 여부를 응답으로 구분해 알리지 않는다.
- 운영에서는 nginx `location /admin`에 IP allow를 거는 것을 권장한다(구현은 배포 단계 범위).
- 로그인 실패 로그에 아이디·비밀번호를 남기지 않는다.

## 9. 테스트 계획

Backend

- 정상 로그인 시 access/refresh cookie 발급
- 틀린 비밀번호 401
- 없는 아이디도 **같은** 401
- 연속 5회 실패 후 잠금, 잠금 중에는 올바른 비밀번호도 실패
- 잠금 해제 시각 이후 정상 로그인
- `role='USER'`인 LOCAL 계정 거부
- 제재(`SUSPENDED`/`BANNED`) 상태의 관리자 거부
- 성공 시 `failed_attempts` 초기화와 `last_login_at` 기록
- 부트스트랩: 환경변수 없으면 계정 미생성, 있으면 upsert 및 해시 갱신

Frontend

- 로그인 폼 제출과 실패 메시지 표시
- `/admin`에서 401을 받으면 `/admin/login`으로 이동
- 관리자가 아닌 계정의 403 화면 유지

## 10. 영향 범위

**바뀌지 않는 것**: JWT 구조, `MemberAccessInterceptor`, 기존 OAuth 로그인 경로,
관리자 API 전부, `admin_actions` 스키마.

**결정이 필요한 것**

1. LOCAL 계정이 `/admin/members` 회원 목록에 노출된다. `AdminMemberService`가 `ROLE_ADMIN`
   대상 제재를 이미 막고 있어 위험은 없지만, 목록에서 숨길지는 별도 결정이 필요하다.
2. 닉네임 중복. `ADMIN_LOCAL_NICKNAME`은 일반 회원과 겹치지 않는 값을 쓴다.
