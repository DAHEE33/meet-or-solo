# 찜(북마크)과 댓글·좋아요 설계

이 문서는 축제와 관광지에 대한 `찜`(북마크), 공개 `댓글`, 댓글 `좋아요` 기능의 화면·DB·로직
설계를 확정하는 문서입니다. 구현은 이 문서의 절 번호를 계약으로 삼습니다.

기획서·WBS에 없던 신규 범위이며, `docs/10_PROGRESS_LOG.md`의 10-B 다음 작업(`신고·안전·후기와
관리자 연계`)보다 먼저 진행하기로 결정했습니다.

## 1. 배경과 대상

`FestivalDetailPage`(`/festivals/:festivalId`)와 `TourSpotDetailPage`(`/spots/:spotId`)에는
현재 저장·의견 기능이 전혀 없습니다. `MyPage`의 `찜한 관광지` 섹션은 `data/mock/tourSpots.ts`
mock이고, 관련 테이블·API·문서도 없는 완전 신규 범위입니다.

찜과 댓글은 모두 **축제 또는 관광지** 두 종류를 대상으로 하며, 두 상세 화면이 같은 컴포넌트와
같은 API 형태를 공유합니다.

## 2. 핵심 설계 판단

### 2.1 비로그인 사용자가 공개 화면에서 튕기지 않아야 한다

`frontend/src/api/apiClient.ts`의 `redirectToLoginIfUnauthorized`는 **모든 `401`을
`window.location.replace('/login')` 전역 리다이렉트**로 처리합니다. 따라서 공개 화면에 붙는
API는 다음을 지켜야 합니다.

- 댓글 목록과 engagement 조회는 비로그인에도 **반드시 `200`** 이다. `401`이면 축제 상세를 열기만
  해도 로그인 화면으로 튕긴다.
- 로그인 여부를 알기 위해 `GET /api/members/me`를 호출하지 않는다. 같은 이유로 튕긴다.
- 그래서 서버가 로그인 여부를 알려주는 공개 엔드포인트를 둔다 —
  `GET /api/festivals/{id}/engagement`가 `viewer.loggedIn`을 함께 반환한다.
- **만료·무효 토큰도 공개 조회에서는 예외를 던지지 않고 비로그인으로 취급한다.** 던지면 위와 같은
  사고가 난다. 감수하는 비용은 쿠키가 만료된 사용자가 자신의 찜 상태를 잠시 보지 못하는 것이고,
  이는 화면 전체가 로그인으로 튕기는 것보다 낫다.

현재 저장소에는 optional-login 패턴이 없다(모든 controller가 `memberId(accessToken)` private
helper를 복사해 쓰고, 쿠키가 없으면 `UNAUTHORIZED`를 던진다). 이번 작업에서 쿠키가 없거나
무효하면 `null`을 반환하는 optional 해석기를 새로 도입한다.

### 2.2 좋아요 카운터는 "실제 영향 행 수"로만 움직인다

`content_comments.like_count`를 비정규화 카운터로 두고, 다음 규칙 하나로 멱등성과 카운터 정합성을
동시에 만족시킨다.

```sql
-- 좋아요 ON
INSERT INTO content_comment_likes (comment_id, member_id) VALUES (?, ?)
  ON CONFLICT (comment_id, member_id) DO NOTHING;          -- affected 0 또는 1
-- affected = 1 일 때만 실행
UPDATE content_comments SET like_count = like_count + 1, updated_at = ? WHERE id = ?;

-- 좋아요 OFF
DELETE FROM content_comment_likes WHERE comment_id = ? AND member_id = ?;   -- affected 0 또는 1
-- affected = 1 일 때만 실행
UPDATE content_comments SET like_count = like_count - 1, updated_at = ? WHERE id = ? AND like_count > 0;
```

- `like_count = like_count ± 1`은 PostgreSQL row-level lock으로 직렬화되므로 lost update가 없다.
- `uq_content_comment_likes_pair`가 멱등성의 근원이고, 연타·동시 요청은 `ON CONFLICT DO NOTHING`
  으로 흡수된다.
- `chk_content_comments_like_count`(`like_count >= 0`)와 `WHERE like_count > 0` 가드가 음수를
  이중으로 막는다.
- 정합성 복구 쿼리는 8.3절에 둔다.

### 2.3 댓글 신고는 이번 범위에서 제외한다

`reports`에는 target 개념이 없다(`reported_member_id NOT NULL` + match group 한정, `target_type`
컬럼·enum 없음). 댓글을 붙이려면 `admin_actions.report_id`,
`match_penalty_events.related_report_id` + `uq_match_penalty_events_related_report`(V25),
`admin_safety_alerts.trigger_report_id`, 그리고 V25가 만든 **30일 유효 신고 누적 → 자동 제재
파이프라인**까지 함께 건드려야 한다. 매너온도·제재 정책 변경이므로 별도 설계가 필요하다.

대신 최소 모더레이션은 이번 범위에서 확보한다.

- 작성자 본인 삭제 (`status = 'DELETED'`)
- 관리자 숨김 (`status = 'HIDDEN'`) — 별도 관리 화면 없이 공개 댓글 섹션에서 관리자에게만
  숨김 버튼을 노출한다. 관리자 여부는 `engagement`의 `viewer.admin`으로 판단하므로 추가 요청이
  없다.

## 3. DB 설계 (`V26__add_content_bookmarks_comments.sql`)

### 3.1 테이블 접두사와 대상 표현

접두사는 `content_`다. 축제와 관광지를 동시에 가리켜 `festival_`/`tour_place_`를 쓸 수 없어,
"관광공사 콘텐츠(축제·관광지)"의 공통 접두사로 새로 도입한다.

대상 표현은 `target_type` + `target_id`가 아니라 **nullable FK 2개 + CHECK**다.

- 근거: `recommendation_click_logs`가 이미 같은 방식(`festival_id`/`tour_place_id`/
  `solo_course_id` nullable FK + CHECK)을 쓰고 있고, FK 참조 정합성을 유지할 수 있다.
- 단 CHECK는 `recommendation_click_logs`의 `OR`(둘 다 채워도 통과) 대신 **정확히 하나**로 조인다 —
  `CHECK ((festival_id IS NOT NULL) <> (tour_place_id IS NOT NULL))`.
- 감수하는 비용: 대상 종류가 3개로 늘면 migration과 조회 분기를 함께 늘려야 한다. 대상이 두
  종류로 고정된 현재 범위에서는 참조 정합성이 더 가치 있다고 판단했다.
- `ON DELETE RESTRICT`가 안전한 이유: 축제 동기화는 사라진 축제를 물리 삭제하지 않고
  `FestivalSyncWriter.markMissingFestivalsInactive`로 `INACTIVE` 표시만 한다.

### 3.2 `content_bookmarks`

```sql
CREATE TABLE content_bookmarks (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    member_id BIGINT NOT NULL,
    festival_id BIGINT,
    tour_place_id BIGINT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_content_bookmarks PRIMARY KEY (id),
    CONSTRAINT fk_content_bookmarks_member   FOREIGN KEY (member_id)     REFERENCES members (id)     ON DELETE RESTRICT,
    CONSTRAINT fk_content_bookmarks_festival FOREIGN KEY (festival_id)   REFERENCES festivals (id)   ON DELETE RESTRICT,
    CONSTRAINT fk_content_bookmarks_place    FOREIGN KEY (tour_place_id) REFERENCES tour_places (id) ON DELETE RESTRICT,
    CONSTRAINT chk_content_bookmarks_target
        CHECK ((festival_id IS NOT NULL) <> (tour_place_id IS NOT NULL))
);
CREATE UNIQUE INDEX uq_content_bookmarks_member_festival
    ON content_bookmarks (member_id, festival_id) WHERE festival_id IS NOT NULL;
CREATE UNIQUE INDEX uq_content_bookmarks_member_place
    ON content_bookmarks (member_id, tour_place_id) WHERE tour_place_id IS NOT NULL;
CREATE INDEX idx_content_bookmarks_member_created_at
    ON content_bookmarks (member_id, created_at DESC, id DESC);
```

`user_blocks`와 같은 구조다 — `(소유자, 대상)` unique pair, `created_at`만, 해제는 물리 삭제.
두 partial unique index가 동시 요청 중복을 DB에서 흡수한다.

### 3.3 `content_comments`

저장소에는 `deleted_at` 단독 soft delete 선례가 없고 **`status` 상태 머신 + 시점 컬럼**이
관용구이므로 그 형태를 따른다.

```sql
CREATE TABLE content_comments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    member_id BIGINT NOT NULL,
    festival_id BIGINT,
    tour_place_id BIGINT,
    body VARCHAR(500) NOT NULL,
    like_count INTEGER NOT NULL DEFAULT 0,
    status VARCHAR(20) NOT NULL DEFAULT 'VISIBLE',
    deleted_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_content_comments PRIMARY KEY (id),
    CONSTRAINT fk_content_comments_member   FOREIGN KEY (member_id)     REFERENCES members (id)     ON DELETE RESTRICT,
    CONSTRAINT fk_content_comments_festival FOREIGN KEY (festival_id)   REFERENCES festivals (id)   ON DELETE RESTRICT,
    CONSTRAINT fk_content_comments_place    FOREIGN KEY (tour_place_id) REFERENCES tour_places (id) ON DELETE RESTRICT,
    CONSTRAINT chk_content_comments_target     CHECK ((festival_id IS NOT NULL) <> (tour_place_id IS NOT NULL)),
    CONSTRAINT chk_content_comments_body       CHECK (char_length(btrim(body)) BETWEEN 1 AND 500),
    CONSTRAINT chk_content_comments_like_count CHECK (like_count >= 0),
    CONSTRAINT chk_content_comments_status     CHECK (status IN ('VISIBLE', 'DELETED', 'HIDDEN')),
    CONSTRAINT chk_content_comments_deleted_at CHECK ((status = 'VISIBLE') = (deleted_at IS NULL))
);
CREATE INDEX idx_content_comments_festival_visible ON content_comments (festival_id, id DESC)
    WHERE status = 'VISIBLE' AND festival_id IS NOT NULL;
CREATE INDEX idx_content_comments_place_visible ON content_comments (tour_place_id, id DESC)
    WHERE status = 'VISIBLE' AND tour_place_id IS NOT NULL;
CREATE INDEX idx_content_comments_member_created_at
    ON content_comments (member_id, created_at DESC, id DESC);
```

- `status`: `VISIBLE` / `DELETED`(작성자 삭제) / `HIDDEN`(관리자 숨김).
- `chk_content_comments_deleted_at`은 V25 `admin_safety_alerts`의 짝 CHECK 관용구(`OPEN`이면
  handled 컬럼이 `NULL`)와 같은 방식이다.
- 목록 정렬 키는 `created_at`이 아니라 **`id DESC`** 다. 동시 삽입 tie-break가 필요 없고 partial
  index가 그대로 적중한다.

### 3.4 `content_comment_likes`

```sql
CREATE TABLE content_comment_likes (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY,
    comment_id BIGINT NOT NULL,
    member_id BIGINT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_content_comment_likes PRIMARY KEY (id),
    CONSTRAINT fk_content_comment_likes_comment FOREIGN KEY (comment_id) REFERENCES content_comments (id) ON DELETE RESTRICT,
    CONSTRAINT fk_content_comment_likes_member  FOREIGN KEY (member_id)  REFERENCES members (id)          ON DELETE RESTRICT,
    CONSTRAINT uq_content_comment_likes_pair UNIQUE (comment_id, member_id)
);
CREATE INDEX idx_content_comment_likes_member
    ON content_comment_likes (member_id, created_at DESC, id DESC);
```

자기 댓글 좋아요는 허용한다. `member_reviews`의 self CHECK와 달리 막을 실익이 없고, CHECK를
추가하면 불필요한 복잡도만 늘어난다.

### 3.5 Migration 적용 주의

V24 헤더 주석 규칙대로, 적용 전 공유 dev DB의 `flyway_schema_history`에서 `V26`이 비어 있는지
확인한다. 다른 담당자가 out-of-band로 적용했으면 checksum 충돌이 난다.
`spring.jpa.hibernate.ddl-auto: validate`이므로 entity와 migration이 정확히 일치해야 부팅된다.

## 4. API 설계

토글은 `POST`/`DELETE` 쌍이 아니라 **`PUT` + 상태 body** 하나로 둔다. 저장소가 이미
`PUT .../cancellation`, `PUT .../acknowledgement`로 쓰는 방식이고, 멱등성과 "현재 카운트를 응답으로
돌려준다"를 동시에 만족한다.

| 메서드 | 경로 | 인증 | 요청 | 응답 |
| --- | --- | --- | --- | --- |
| GET | `/api/festivals/{id}/engagement` | 선택 | — | `200 {bookmarked, commentCount, viewer:{loggedIn, admin}}` |
| PUT | `/api/festivals/{id}/bookmark` | 필수 | `{bookmarked}` | `200 {bookmarked}` |
| GET | `/api/festivals/{id}/comments?page&size` | 선택 | — | `200` 페이지 응답 |
| POST | `/api/festivals/{id}/comments` | 필수 | `{body}` | `201` 댓글 항목 |
| DELETE | `/api/comments/{commentId}` | 필수 | — | `204` |
| PUT | `/api/comments/{commentId}/like` | 필수 | `{liked}` | `200 {liked, likeCount}` |
| PUT | `/api/admin/comments/{commentId}/visibility` | 관리자 | `{visible}` | `200 {visible}` |
| GET | `/api/members/me/bookmarks?type&page&size` | 필수 | — | `200` 페이지 응답 |

`/api/spots/{id}/engagement`, `/api/spots/{id}/bookmark`, `/api/spots/{id}/comments`가 같은
형태로 대칭 존재한다. 관광지 URL 세그먼트는 기존 규칙대로 `/api/spots`이고 path variable은 내부
`id`다(`contentId` 아님).

`type`은 `FESTIVAL` | `TOUR_PLACE`이고 기본값은 `FESTIVAL`이다.

페이지 응답은 기존 공개 목록과 동일한 `{items, page, size, totalElements, totalPages, hasNext}`
형태로 통일해 프론트의 `useInfiniteList`를 그대로 재사용한다.

### 4.1 댓글 항목 응답

```json
{
  "id": 1024,
  "nickname": "춘천사람",
  "body": "작년에도 갔는데 야간 조명이 좋았어요",
  "likeCount": 4,
  "likedByMe": false,
  "mine": false,
  "createdAt": "2026-09-07T10:12:00+09:00"
}
```

`memberId`는 **노출하지 않는다.** 차단·신고 연동이 없어 필요가 없고, `docs/06_SECURITY_POLICY.md`의
내부 ID 미노출 기조에 맞춘다. `mine`만으로 삭제 버튼 노출을 판단한다.

`profileImageUrl`도 노출하지 않는다(6.2절).

## 5. 로직 설계

### 5.1 찜 토글 — `PUT /api/{festivals|spots}/{id}/bookmark`

`@Transactional`

1. 인증 필수. `SUSPENDED`/`BANNED`/비활성 회원은 기존 `MemberAccessInterceptor`가 `/api/**`에서
   자동으로 차단하므로 별도 구현하지 않는다.
2. 대상이 존재하고 `status <> 'HIDDEN'`인지 검증한다. 아니면 `NOT_FOUND`.
3. `bookmarked = true`면 `INSERT ... ON CONFLICT DO NOTHING`, `false`면 `DELETE`(없어도 성공).
4. 응답은 항상 요청한 상태를 그대로 돌려준다. 동시 `true` 2건은 partial unique index가 1건만
   남기고 둘 다 `200`이다.

지난 축제(`ENDED`)와 `INACTIVE` 대상도 **찜을 허용한다.** 사용자가 명시적으로 저장한 항목이
동기화 사정으로 사라지면 안 된다. `HIDDEN`만 막는다(공개 조회에서 이미 제외되는 대상).

### 5.2 댓글 등록 — `POST /api/{festivals|spots}/{id}/comments`

`@Transactional`

1. 인증 필수.
2. `members.status`가 `PROFILE_REQUIRED`면 거절한다. 닉네임이 없어 표시할 이름이 없다.
3. `body`를 trim한 뒤 1~500자를 검증한다.
4. 대상이 존재하고 `HIDDEN`이 아닌지 검증한다.
5. **도배 완화**: 같은 회원의 마지막 댓글이 5초 이내면 `429`.
   - `idx_content_comments_member_created_at`으로 조회한다.
   - **한계**: 동시 요청 2건은 둘 다 통과할 수 있다. 사람이 연타하는 수준만 막는 완화책이며,
     엄격히 막으려면 회원 단위 advisory lock이 필요해 MVP 과잉으로 제외했다.
6. INSERT 후 `201`과 생성 항목(`likeCount: 0`, `likedByMe: false`, `mine: true`)을 반환한다.

### 5.3 댓글 삭제 — `DELETE /api/comments/{commentId}`

`@Transactional`

```sql
UPDATE content_comments
   SET status = 'DELETED', deleted_at = ?, updated_at = ?
 WHERE id = ? AND member_id = ? AND status = 'VISIBLE';
```

- affected가 0이면 이미 삭제된 것으로 보고 그대로 `204`를 반환한다(멱등).
- 대상 댓글이 존재하고 `VISIBLE`인데 작성자가 다르면 `FORBIDDEN`이다.
- 좋아요 row는 남긴다. 목록에서 제외되어 노출되지 않고, `ON DELETE RESTRICT`라 물리 삭제가
  애초에 막혀 있다.

### 5.4 좋아요 토글 — `PUT /api/comments/{commentId}/like`

`@Transactional`. 2.2절 규칙을 그대로 구현한다.

- 대상 댓글이 `VISIBLE`이 아니면 `NOT_FOUND`.
- 응답은 토글 후의 `{liked, likeCount}` 실제값이다.

### 5.5 댓글 목록 — `GET /api/{festivals|spots}/{id}/comments`

`@Transactional(readOnly = true)`, 공개.

1. optional 회원 해석 — 쿠키 없음/만료/무효를 전부 `null`로 취급한다(2.1절).
2. `WHERE festival_id = ? AND status = 'VISIBLE' ORDER BY id DESC` + offset 페이징. 3.3절의
   partial index가 적중한다.
3. 내 좋아요는 `comment_id IN (:ids)` 한 번으로 조회해 N+1을 만들지 않는다(총 2~3쿼리).
4. `totalElements`로 화면의 `댓글 N`을 표시한다.
5. **알려진 한계**: offset 페이징이라 다음 페이지 요청 전에 새 댓글이 달리면 1건이 중복될 수 있다.
   프론트에서 `id` 기준 dedupe로 완화하고, cursor(`beforeId`) 전환은 9절 확장 항목으로 둔다.
   기존 공개 목록 API가 전부 offset이라 `useInfiniteList` 재사용을 택했다.

### 5.6 관리자 숨김 — `PUT /api/admin/comments/{commentId}/visibility`

`AdminAuthorizationService.requireAdmin`을 service 첫 문장에서 호출한다(최신 admin 서비스 패턴).
`visible = false`면 `status = 'HIDDEN'` + `deleted_at`, `true`면 `VISIBLE` + `deleted_at = NULL`로
되돌린다. 작성자가 삭제한 `DELETED`는 관리자가 되살리지 않는다.

응답은 `{visible, changed}`다. `changed = false`는 재공개 요청이 아무 일도 하지 않았다는 뜻이고,
관리자 화면이 "작성자가 이미 삭제한 댓글이라 되살릴 수 없다"를 구분할 수 있는 유일한 수단이다.

### 5.7 회원 상태 연동

| 상황 | 댓글 | 찜 | 근거 |
| --- | --- | --- | --- |
| 정지(`SUSPENDED`) | 유지, 신규 작성만 차단 | 유지 | 일시 조치다. 기존 공개 글을 지우면 다른 사용자의 대화 맥락이 깨진다. 신규 차단은 `MemberAccessInterceptor`가 자동 처리 |
| 탈퇴(`WITHDRAWN`/`DELETED`) | `VISIBLE` → `DELETED` 일괄 전환 | 물리 삭제 | 탈퇴 시 닉네임·이미지를 익명화하는 기존 정책(`docs/11_DATABASE_DESIGN.md` 개인정보 보관)과 일관. 공개 콘텐츠로 남기면 개인정보 삭제 요구와 충돌 |

**탈퇴 연동은 아직 호출되지 않는다.** `ContentCommentService.softDeleteAllOnWithdrawal`과
`ContentBookmarkService.deleteAllOnWithdrawal`은 구현·단위 테스트까지 되어 있지만, 이 저장소에는
**회원 탈퇴 서비스 자체가 없다** — `members.withdrawn_at` 컬럼만 있고 회원 controller에 탈퇴
endpoint가 없다(문서에 등장하는 `DELETE /api/members/me`는 아직 구현되지 않았다). 탈퇴 기능을
만드는 담당자가 같은 transaction에서 두 메서드를 호출해야 하며,
`ContentCommentService`에 그 취지의 TODO 주석을 남겼다.

## 6. 개인정보와 보안

### 6.1 본문은 암호화하지 않는다

공개 댓글이므로 평문으로 저장한다. `member_reviews.comment_encrypted`와 반대인 이유는 그쪽이
비공개 상호 평가라서다.

### 6.2 작성자 아바타는 닉네임 이니셜만 — 프로필 이미지는 노출하지 않는다

- 타인 프로필 이미지 노출 선례(`MatchGroupMemberRepository`가 `member.profile_image_url`을
  내려주는 것)는 **같은 매칭 그룹의 인증 회원 한정**이다. 댓글은 비로그인 포함 전체 공개다.
- 카카오·네이버 OAuth 프로필 사진을 공개 웹에 노출하려면 별도 동의·정책 검토가 필요하다.
- 직접 업로드한 이미지는 private bucket 본인 전용 중계(`GET /api/members/me/profile-image`)라
  애초에 타인에게 쓸 수 없다.

따라서 댓글 작성자는 **닉네임 + 닉네임 첫 글자 이니셜 아바타**로만 표시한다.

### 6.3 노출하지 않는 값

`memberId`, `profileImageUrl`, 이메일, OAuth 식별자, 회원 상태, penalty/cooldown, 내부 댓글
`status`를 공개 응답에 담지 않는다.

## 8. 운영 쿼리

### 8.1 특정 축제 댓글 수

```sql
SELECT count(*) FROM content_comments WHERE festival_id = ? AND status = 'VISIBLE';
```

### 8.2 회원별 찜 수

```sql
SELECT member_id, count(*) FROM content_bookmarks GROUP BY member_id ORDER BY 2 DESC;
```

### 8.3 `like_count` 정합성 복구

```sql
UPDATE content_comments c SET like_count = s.cnt
FROM (SELECT comment_id, count(*) AS cnt FROM content_comment_likes GROUP BY comment_id) s
WHERE c.id = s.comment_id AND c.like_count <> s.cnt;
```

좋아요가 한 건도 없는 댓글은 위 쿼리에 잡히지 않으므로, 전수 검증이 필요하면
`LEFT JOIN`으로 바꾼다.

## 10. 테스트 우선순위

Backend (Testcontainers `pgvector/pgvector:pg16`, fixture id `9_xxx_xxx` 대역)

1. **좋아요 카운터** — 중복 ON은 1, 동시 ON 2건도 1, OFF 후 ON은 1, OFF 2번은 0 유지(음수 방지)
2. **찜 멱등** — ON 2번은 row 1건, OFF 2번도 성공
3. 삭제된 댓글은 목록에서 제외되고 그 댓글 좋아요는 `NOT_FOUND`
4. **비로그인 목록은 `200`이고 `likedByMe = false`, 만료 토큰도 `200`** — 2.1절 회귀 방지
5. 남의 댓글 삭제는 `FORBIDDEN`
6. 탈퇴 시 댓글 일괄 `DELETED`
7. 도배 완화 5초 규칙

Frontend (node 환경, jsdom 없음 → 결정 로직은 순수 함수 또는 세션 팩토리로 뽑는다)

8. `createContentCommentsSession` 상태 전이, 이중 제출 흡수, `stop()` 후 늦은 응답 무시
9. 본문 검증 순수 함수(trim, 1~500자)
10. `id` 기준 dedupe 함수 — 5.5절 한계 완화
11. `formatRelativeTime` 경계값
12. 두 상세 화면 SSR 마크업에 댓글 섹션과 찜 버튼이 존재

### 10.1 항목 12의 실제 구현

두 상세 화면은 `loading: true`로 시작하므로 SSR 마크업이 로딩 분기에서 끝나고, 찜 버튼과 댓글
섹션이 있는 로드 완료 분기에 도달하지 못한다. 그래서 마크업 단정 대신 **실제 correctness 규칙**을
순수 함수로 뽑아 고정했다 — `resolveBookmarkAction(state) → 'LOGIN' | 'TOGGLE' | 'IGNORE'`.
두 화면이 이 함수를 공유하므로 2.1절 회귀(비로그인 사용자에게 요청을 보내 화면째로 튕기는 것)를
막는다. 섹션·항목·폼·버튼 컴포넌트의 SSR 마크업은 개별로 검증하고, 두 화면에는 배선이 깨지면
실패하는 SSR smoke 테스트를 남겼다.

`ContentBookmarkCommentIntegrationTest`(10절 1~6 항목 + 관리자 숨김, 24건)는 **컴파일만 되고 한
번도 실행되지 않았다.** 작업 머신에 Docker가 설치되어 있지 않아 Testcontainers가
`ContainerFetchException`으로 실패한다. 이 저장소의 Spring context 테스트는
`MeetOrSoloApplicationTests.contextLoads`를 포함해 전부 Testcontainers를 요구하므로 Docker 없는
우회 경로가 없다.

그래서 다음 두 가지가 **런타임으로 검증되지 않았다.**

- 신규 repository의 JPQL이 Hibernate bootstrap에서 파싱되는지
- `ddl-auto: validate`가 신규 entity와 V26을 일치로 판정하는지

Docker 없이 가능한 범위는 정적으로 교차 확인했다 — 참조하는 모든 entity 경로가 실제 필드명과
일치하고(특히 `Festival`의 필드명은 `regionCode`가 아니라 **`areaCode`**, 응답 DTO에서만
`regionCode`로 노출된다), constructor projection record의 타입이 selection 타입과 맞고
(모두 wrapper 타입이라 primitive 해석 위험을 피한다), entity 컬럼명·nullable·length가 V26 DDL과
일치한다.

**Docker가 있는 환경에서 통합 테스트와 애플리케이션 부팅을 한 번 돌려 확인해야 한다.** 그 전까지
이 기능은 "코드 완성, 런타임 미검증"으로 취급한다.

Gradle 실행 시 참고 — 이 머신의 `JAVA_HOME`은 JDK 8을 가리키므로
`JAVA_HOME="C:\java\zulu17"`을 지정해야 빌드된다.
