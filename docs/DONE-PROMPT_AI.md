# 취향 임베딩 매칭 반영 — 실측 결과와 남은 판단

- 작성: 2026-09-19
- 브랜치: `fix/wbs-10-b-matching-scheduler-only` (`origin/dev` 8b25ba0 기준)
- 커밋: `7b77a0f`(즉시 조합 경로 제거), `d24ba4f`(수집 주기 기본값 10s)
- 상태: **구조 수정과 로컬 회귀 테스트 완료. dev 재현 검증 미실시. 정책 판단 5건 미결.**

이 문서는 **사실과 추론을 구분해서** 적는다. 확인한 것과 확인하지 않은 것을 섞으면 다음 판단이
틀어진다. 각 절에 "확인한 것 / 확인하지 않은 것"을 명시했다.

## 1. 무엇을 하려고 했나

개발계에서 테스터 5명으로 "취향 임베딩이 매칭 결과에 실제로 반영되는가"를 확인하려 했다.

설계 근거는 이렇다. 여행스타일 태그를 전원 동일하게 고정하면 모든 pair의 Jaccard가 상수가 되므로
총점 순위가 코사인만으로 갈린다. 다만 이것이 성립하려면 조건이 있다.

- **후보 전원이 유효한(`COMPLETED`) 임베딩을 보유**해야 한다. 한 명이라도 없으면 그 pair는
  fallback으로 Jaccard만 쓰이고(`PairCompatibilityScorer.scoreDetailed()`), 상수 가정이 깨진다
- **임베딩 가중치가 양수**여야 한다. 0이면 코사인이 총점에 기여하지 않는다
- **반올림 동점이 없어야** 한다. 점수는 소수 둘째 자리에서 반올림되므로 코사인 차이가 충분히
  작으면 동점이 되고, 그때는 대기 시각과 pool id가 순위를 가른다

이 조건들이 만족되는 범위에서는 가중치 값 자체(0.70/0.30이든 0.50/0.50이든)와 무관하게 예상
짝이 같다.

## 2. 관찰된 현상

결과가 취향과 무관하게 **먼저 신청한 사람끼리** 묶였다. 두 명씩 따로 매칭됐고, 취향이 가장 가까운
조합은 만들어지지 않았다.

## 3. 실측 — dev DB 직접 조회

dev DB는 조회만 했다(`docs/08`). 접속 경로는 9절에 적었다.

### 3.1 검증 1 — 임베딩 생성·저장은 정상이었다

| member_id | embedding_status | vector | model | 태그 |
| --- | --- | --- | --- | --- |
| 2, 3, 4, 6, 281 | 전원 `COMPLETED` | 있음 | `text-embedding-3-small` | 전원 `FOOD,PHOTO` |

`embedding_error_reason` 0건. **데이터 가설은 기각됐다.**

이 검증이 필요했던 이유는 `PairCompatibilityScorer.scoreDetailed()`가 한쪽이라도 임베딩이 없으면
**경고 없이** Jaccard 점수만 쓰고 `embedding_applied = false`로 남기기 때문이다
(`EmbeddingScorer.score()`가 null 반환). 즉 데이터 문제도 같은 증상을 만든다. 실제로 09-17
attempt 56은 `embedding_applied = f`였다(당시 member 5에 임베딩이 없었다).

### 3.2 검증 2 — 임베딩은 적용됐으나 선택에 반영되지 않았다

09-18 22:06 마지막 라운드.

| attempt | 시각 | 짝 | jaccard | cosine | member_score | embedding_applied | created_by |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 61 | 22:06:**46** | 2 + 281 | 100.00 | 52.61 | 76.31 | `t` | **POOL_ENTRY** |
| 62 | 22:06:**47** | 3 + 6 | 100.00 | 55.05 | 77.53 | `t` | **POOL_ENTRY** |

**확인한 것**

- `created_by = POOL_ENTRY` → **즉시 조합 경로가 실행됐다.** scheduler tick이 만든 attempt가 아니다
- 두 attempt가 1초 간격으로 **따로** 생성됐다 → 한 번의 평가에서 5명을 놓고 고른 것이 아니다
- `embedding_applied = t`, `jaccard_score = 100.00` → 임베딩이 실제로 적용됐고 태그도 상수였다.
  즉 점수는 계산·저장됐다
- 선택된 두 조합이 코사인 상위 조합이 아니다(3.3)

**확인하지 않은 것**

- **각 attempt가 만들어진 순간 후보가 정확히 몇 명이었는지는 모른다.** 그 시점의 `match_pools`
  상태를 스냅샷으로 남겨두지 않았고, 이후 상태가 바뀌었다. "후보가 2명뿐이었다"는 코드 구조상
  가장 그럴듯한 설명이지 조회로 확인한 사실이 아니다
- 두 attempt가 1초 차이인 것은 **즉시 경로가 두 번 따로 돌았다**는 것과 정합적이지만, 그 자체가
  후보 수를 증명하지는 않는다

### 3.3 코사인 행렬 — 1·2순위가 아니라 5·6순위가 선택됐다

```
 2–6    70.37   ← 1순위
 3–281  60.80   ← 2순위
 4–6    59.99
 6–281  56.01
 3–6    55.05   ← 실제 attempt 62
 2–281  52.61   ← 실제 attempt 61
 3–4    52.10
 4–281  51.54
 2–4    50.49
 2–3    46.97
```

| | 짝 | 코사인 평균 |
| --- | --- | --- |
| 점수대로 골랐다면 | 2–6, 3–281 (4번 제외) | **65.59** |
| 실제 결과 | 2–281, 3–6 (4번 제외) | 53.83 |

**전제 — 이 행렬은 2026-09-19 시점에 조회한 벡터로 계산했다.** 매칭이 일어난 09-18 22:06
당시의 벡터와 같다는 근거는 `member_preference_embeddings.updated_at`이 22:00~22:03으로
attempt 생성 시각보다 이르고 그 뒤로 갱신 기록이 없다는 것이다(`@PreUpdate`로 갱신되는 컬럼).
다만 JPA를 거치지 않은 직접 `UPDATE`는 이 컬럼을 바꾸지 않으므로, 그런 조작이 없었다는 가정 위에
성립한다. 저장된 `cosine_score`(52.61, 55.05)가 현재 벡터로 계산한 값과 일치하는 것도 같은
방향의 방증이다.

## 4. 원인 판단과 조치

**가장 잘 설명하는 가설**: 조합 경로가 둘이었고 즉시 경로가 점수가 개입할 여지를 없앴다.

- `MatchPoolEntryService:110` → `MatchingPoolEnteredEvent` 발행
- `MatchingPoolEnteredEventHandler:22` → `@TransactionalEventListener(AFTER_COMMIT)`으로 즉시 조합

즉시 경로는 **유효한 조합이 처음 생기는 순간 소진**시킨다. 대기 후보가 2명을 넘지 못하고, 조합이
1개면 정렬해서 고를 대상이 없다. `MATCHING_SCHEDULER_ENABLED`와 무관하게 항상 돌았고 끄는
플래그도 없었다. `docs/05` 매칭 흐름 3번은 이미 scheduler 기준이었으므로, 제거는 새 정책이 아니라
코드를 문서에 맞추는 변경이었다.

**이 가설을 뒷받침하는 것**: `created_by = POOL_ENTRY`(경로 실행 확인), 선택된 조합이 점수
상위가 아님, 8절의 로컬 회귀 테스트(같은 배치에 5명이 있으면 점수대로 선택된다).

**아직 남은 것**: 당시 실제 후보 구성(3.2)과 dev에서 고쳐진 뒤의 재현(7절).

조치(커밋 2건):

- 즉시 경로 4개 클래스와 `findPoolEntryClaimablePoolsForUpdate` 제거
  (그 쿼리에만 남아 있던 `preferred_group_size` 버킷 필터가 함께 해소됨)
- `MATCHING_SCHEDULER_ENABLED` 기본값 `true`, `MATCHING_SCHEDULER_FIXED_DELAY` 기본값 `10s`
- `MatchGroupComposerTest`에 임베딩 케이스 3건 추가(이 파일에 임베딩 테스트가 **하나도 없었다**)
- `docs/02`, `docs/05`, `docs/30` 7절, `docs/32` 항목 G, `docs/10`

전체 테스트 1098건 중 36건 실패로 기존 baseline과 동일(34건 dev DB 터널 미연결, 2건 기존 실패).
**매칭 관련 실패 0건.**

## 5. 새로 드러난 것 — 저장 점수가 0.50/0.50 계산과 일치한다

| attempt | 0.50/0.50 계산 | 0.70/0.30 계산 | 저장값 |
| --- | --- | --- | --- |
| 61 | `0.5×100 + 0.5×52.61` = **76.31** | 85.78 | **76.31** |
| 62 | `0.5×100 + 0.5×55.05` = **77.53** | 86.52 | **77.53** |

**확인한 것**: dev에 저장된 `member_score`는 가중치 0.50/0.50으로 계산한 값과 일치하고,
0.70/0.30과는 일치하지 않는다. `application.yml` 기본값과 `.env.dev.example`은 0.70/0.30이다.

**확인하지 않은 것**: **그 값이 어디서 주입되는지는 확인하지 않았다.** 서버 설정을 직접 보지
않았으므로 `.env`라고 단정할 수 없다. compose 파일의 environment, 컨테이너 환경변수, 다른
property source 중 어디든 가능하다. 참고로 `scripts/verify-embedding-score.sql`도
`jw 0.50 / ew 0.50`으로 적혀 있어 이전부터 이 값이 쓰였을 가능성이 있다.

이번 분석 결론은 이 불일치와 무관하다. 1절 조건이 만족되는 범위에서 순위는 코사인만으로
정해지기 때문이다. 다만 **설정이 갈라져 있다는 사실 자체가 정리 대상**이다.

## 6. 판단이 필요한 것

### 6.1 가중치를 어디에 맞출 것인가 (우선)

| 안 | 내용 | 평가 |
| --- | --- | --- |
| **A. 서버를 0.70/0.30으로** | 코드 기본값·example에 맞춘다 | 코드·문서·서버가 일치한다 |
| **B. 기본값·example을 0.50/0.50으로** | 실제 쓰이는 값에 맞춘다 | 현실 반영. `PairCompatibilityScorer` 주석의 "태그를 주 신호로" 근거와 어긋난다 |
| **C. 둘 다 두고 명시만** | 실험값이라고 문서화 | 지금 상태. 어느 값이 맞는지 모르는 채로 남는다 |

**A를 제안하되, 이것은 설정 일관성을 위한 제안이지 0.70/0.30이 매칭 품질에서 더 낫다는 검증은
아니다.** 어느 배분이 더 나은지는 실사용 데이터 없이 판단할 수 없고, 가중치는 실사용 데이터로
조정할 값이라고 코드 주석에 이미 적혀 있다. 지금 B를 택하면 근거 없이 0.50을 고정하는 셈이고,
A를 택해도 마찬가지로 "근거 있는 값"이 되는 것은 아니다. 차이는 **코드·문서·서버가 같은 값을
가리키느냐**뿐이다.

선행 작업: 실제 주입 출처부터 확인해야 한다(5절).

### 6.2 최소 궁합 점수 임계값을 둘 것인가

현재 임계값이 없다. 점수가 0이어도 유효한 조합이면 매칭된다. 점수는 조합 간 순위만 가리고,
그 순위도 인원 수보다 뒤다.

| 안 | 효과 | 대가 |
| --- | --- | --- |
| 도입 안 함(현행) | 매칭 성공률 최대 | 궁합이 나빠도 성사. 후보가 적으면 점수가 사실상 무력 |
| 임계값 도입 | 나쁜 매칭 차단 | **후보가 적을 때 실패율 급증** → 솔로 코스로 밀림 |

수집 주기 전환 후 실제 점수 분포를 본 뒤 판단해야 한다. 분포를 모르는 상태에서 숫자를 정하면
근거 없는 값이 하나 더 생긴다.

### 6.3 "더 나은 상대를 기다리는" 정책을 둘 것인가

수집 주기는 후보가 모일 **기회**를 주지만 보장하지 않는다. 그 10초에 두 명만 모이면 여전히 그
둘이 매칭된다. 이것은 밀도의 한계가 아니라 **임계값 없이 지금 가능한 조합을 즉시 선택하는 현재
정책의 결과**다.

"탐색 60초를 끝까지 써서 최적 조합을 고른다"는 아이디어는 타당하지만, **수집 주기를 60초로
늘리는 것으로는 구현되지 않는다.** 세 scheduler가 주기를 공유하므로:

| | 틱 10초 | 틱 60초 |
| --- | --- | --- |
| 한 사람이 받는 평가 기회 | 6회 | 1회 이하(진입 시점에 따라 0회, 만료와 레이스) |
| 30초 제안이 닫히는 시점 | 30~40초 | 30~90초 |
| 만남 종료·stale 정리 해상도 | 10초 | 60초 |

별도 정책(대기 유보)으로 설계해야 하며 코드 변경 범위가 크다. 이번 범위 밖이다.

### 6.4 후보가 적을 때의 선착순을 제품으로 수용할 것인가

아래 표는 **"10초 동안 신규 유효 신청이 3건 이상 발생할 확률"** 이다(도착을 포아송 과정으로
가정). 2인 매칭에서 조합이 2개 이상 생기려면 유효 후보가 3명 이상이어야 하므로 그 근사치다.

| 신청률 | 10초 동안 신규 유효 신청 3건 이상 |
| --- | --- |
| 2명/분 | 0.5% |
| 6명/분 | 8.0% |
| 12명/분 | 32.3% |
| 30명/분 | 87.5% |

**이 표는 실제 "점수가 개입한 매칭 비율"이 아니다.** 다음을 포함하지 않는다.

- **직전 틱에서 묶이지 못하고 남은 대기자.** 실제 배치는 신규 신청 + 잔여 대기자이므로 실제
  확률은 이보다 높다
- 차단·쿨타임·재매칭 제외로 후보에서 빠지는 경우(낮추는 방향)
- 희망 인원이 섞여 조합이 성립하지 않는 경우(낮추는 방향)
- 신청률이 시간대·축제별로 크게 달라진다는 점. λ 추정치는 아직 없다

즉 이 표는 **λ를 알면 답이 나온다는 틀**이지 현장 예측이 아니다.

**"AI 임베딩 매칭"을 대외적으로 설명한다면 이 한계를 먼저 정해야 한다.** 화면 문구와 문서에서
"AI가 궁합을 분석한다"로 표현하지 않기로 했다. "입력한 취향의 유사도를 점수에 반영한다"가
사실에 맞다.

### 6.5 임베딩 점수와 실제 만족도의 관계를 검증할 것인가

코사인 유사도는 **회원이 입력한 취향 문장의 의미적 유사도**이고, 실제 사람 사이의 궁합이나 만남
만족도를 검증한 점수가 아니다. 보조 신호로 쓰는 것은 타당하지만 만족도와의 관계는 별도 검증이
필요하다.

후속 경로 후보: 만남 후 `member_reviews`, 매너온도 변화와 당시
`match_attempt_members.cosine_score`의 상관. 표본이 쌓여야 가능하므로 지금은 데이터를 남기는
것으로 충분하다(V24 분해값 저장이 이미 그 역할을 한다).

| 전원 희망 인원 **2명** | `match_pools.preferred_group_size` |
| 태그 동일 | `member_travel_styles` |
| 전원 유효한(`COMPLETED`) 임베딩 보유 | `member_preference_embeddings.embedding_status` |
| 차단 없음 | `user_blocks` |
| 재매칭 제외 없음 | `match_opponent_exclusions` (직전 라운드에서 **거절**하면 생긴다) |
| 쿨타임 없음 | `match_cooldowns` |
| 체크인 유효 | `festival_checkins` ACTIVE, 1시간 이내 |

**신청이 스케줄러 틱 경계를 걸치면 다른 결과가 나온다.** 5명이 같은 10초 창에 들어오지 못하고
일부가 다음 틱으로 넘어가면, 먼저 평가된 배치에서 일부가 먼저 묶이고 남은 사람은 다음 배치에서
평가된다. 이것은 결함이 아니라 설계대로 동작한 것이다.

### 기대 결과

| | 기대 |
| --- | --- |
| 짝 | **2–6 (코사인 70.37)**, **3–281 (60.80)** |
| 남는 사람 | 4번 → 매칭 실패 → 솔로 코스 전환 |
| attempt | `created_by = SCHEDULER`, 한 tick에서 2건 |
| `match_attempt_members` | `jaccard_score` 전원 동일, `cosine_score`만 다름, `embedding_applied = t` |

dev 서버에 `MATCHING_SCHEDULER_FIXED_DELAY=10s` 반영과 재기동이 선행돼야 한다.

### 결과가 다르게 나오면

**추가 결함으로 단정하기 전에 실제 배치 구성과 제외 사유부터 확인한다.** 위 조건 중 하나만
어긋나도 다른 결과가 정상이다.

1. 두 attempt의 `created_by`가 `SCHEDULER`인가 (`POOL_ENTRY`면 배포가 반영되지 않은 것)
2. 두 attempt의 `started_at`이 같은 tick인가, 아니면 틱을 걸쳤는가
3. `match_attempt_members`의 `embedding_applied`와 `jaccard_score` — 한 명이라도 임베딩이
   빠졌거나 태그가 달랐으면 상수 가정이 깨진다
4. `user_blocks` / `match_opponent_exclusions` / `match_cooldowns`에 해당 회원이 있는가
5. 남은 사람의 pool이 `WAITING`인가 `EXPIRED`인가

## 8. 로컬 회귀 테스트 (이번에 추가)

`MatchingOrchestrationServiceIntegrationTest`에 2건을 추가했다. Testcontainers(pgvector)로
실제 PostgreSQL에 벡터를 넣고 **scheduler가 쓰는 조합·제안 생성 경로(`runTick()`)를 한 번**
실행한다. **외부 임베딩 API는 호출하지 않는다.**

기존 테스트와 중복되지 않는다.

| 기존 | 무엇을 보는가 |
| --- | --- |
| `DB에_저장된_임베딩이_scheduler_tick을_거쳐_점수_분해_컬럼에_반영된다` | 후보가 정확히 4명이라 조합이 하나뿐. **점수 분해값이 컬럼까지 도달하는가** |
| `MatchGroupComposerTest` 신규 3건 | 조합기 단위. DB·제안 생성·`created_by`는 다루지 않는다 |
| `PairCompatibilityScorerTest` | 점수 산술과 fallback |

추가한 것은 **조합이 여러 개일 때 무엇이 선택되는가**다.

| 테스트 | 내용 |
| --- | --- |
| `같은_배치의_후보_5명_중_신청순서가_아니라_임베딩_점수로_두_조합이_선택된다` | 후보 5명, 전원 희망 2명·태그 동일(fixture의 `PHOTO`)·고정 벡터. 신청 순서는 1→2→6→10→11이라 순서대로면 (1,2)·(6,10)이고 11이 남는다. 점수대로면 (1,10)·(2,11)이고 6이 남는다. **후자를 검증한다** |
| `임베딩을_맞바꾸면_선택되는_조합도_바뀐다` | 회원·신청 순서·태그를 그대로 두고 9110010과 9110011의 벡터만 교환 → 기대 조합이 (1,11)·(2,10)으로 바뀐다 |

함께 검증하는 것: 남은 한 명의 pool이 `WAITING`으로 남는지, `match_attempts.created_by`가
`SCHEDULER`인지, 모든 회원의 `jaccard_score = 100.00`과 `embedding_applied = true`인지
(태그가 상수였고 임베딩이 실제 적용됐다는 것까지 확인해야 점수 검증이 성립한다).

벡터는 앞 두 성분만 쓰는 단위 벡터를 각도로 설계했다. 0°(1) / 90°(2) / 45°(6) / 2°(10) /
85°(11)이므로 코사인 1위가 1-10, 2위가 2-11이다.

**이 테스트가 검증하지 않는 것**

- **실제 임베딩 모델의 품질.** 고정 벡터를 쓰므로 `text-embedding-3-small`이 한국어 취향
  문장을 잘 구분하는지는 무관하다
- **dev 배포 결과.** 로컬 컨테이너에서 코드 경로만 검증한다. 서버 설정·배포 반영은 7절이다
- **임베딩 점수와 실제 만남 만족도의 관계**(6.5)

## 9. 검증 재현 방법

dev DB는 조회 전용이다(`docs/08`). 쓰기가 필요한 시나리오는 로컬에서 한다.

```powershell
# 터널. 기존에 떠 있던 ssh 셸에는 -L이 없어 로컬 15432가 열리지 않는다.
powershell -File scripts/start-dev-db-tunnel.ps1
```

`psql`이 PATH에 없으면 Docker로 붙는다. 자격증명은 저장소 루트 `.env`에서 읽고 출력하지 않는다.

```bash
set -a && . ./.env && set +a
docker run --rm -e PGPASSWORD="$POSTGRES_PASSWORD" postgres:16 \
  psql -h host.docker.internal -p 15432 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "<query>"
```

> IntelliJ Database의 **내장 SSH 터널은 로컬 포트를 열지 않는다.** IntelliJ에서는 조회가 되는데
> gradle·psql은 붙지 못하는 원인이 이것이다. 다른 프로세스가 써야 하면 위 스크립트를 쓴다.

조회 쿼리는 `docs/30` 7절에 있다.
